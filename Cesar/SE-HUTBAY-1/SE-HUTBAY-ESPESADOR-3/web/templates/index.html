Filtros Exp-Q

Suavizado (q, ventana_s) por variable de proceso, una por cada tag de categoria PV. La ventana se mide en segundos de proceso, no en muestras: el motor corre en ciclo libre y el suavizado vale igual sin importar a que velocidad gire el lazo. Se aplica al iniciar el motor. Toda PV necesita filtro: si llega una sin configurar, el tick falla.

Variable q (0.0 - 1.0) ventana_s (0.1 - 3600 s) Tag / unidad

Defuzzy

Aca viven las variables manipuladas: lo que el experto mueve en la planta, a diferencia de las variables de proceso (Fuzzy), que solo mide. Cada familia es un tag de categoria SP y su tabla Sugeno traduce la conviccion de una regla en cuanto se mueve ese setpoint.
Las filas son acciones con nombre libre — el nombre es lo que las reglas ponen en su then — y las columnas son puntos del belief, de menor a mayor.

Fuzzy

Membresias por variable de proceso. Cada tag PV tiene su propia tabla, todas a la vista: las que todavia no tienen membresia aparecen en rojo con su boton para crearla. La primera fila es el offset (el eje); debajo va una fila por etiqueta, con nombre libre — HIGH/OK/LOW es solo la plantilla. Cada tabla se guarda por separado. Se aplica al iniciar el motor.

Fuzzy de pendiente

La tendencia de una variable, no su valor: cuanto sube o baja por minuto. Se puede crear mas de una por variable, con ventanas distintas — una corta para detectar un arranque, una larga para una deriva lenta. El eje esta en unidades de ingenieria por minuto. El nombre queda congelado al crearla: cambiar la ventana no rompe las reglas que la nombran.

Contrato de Variables

Que variables controla el experto en esta planta. El producto viene con una plantilla estandar (espesador completo) y aqui se moldea al cliente: se quitan las variables que no estan instrumentadas y se agregan las que si. Antes esta lista vivia en el codigo.

¿Para que sirve el contrato?

Es la lista de variables que el experto reconoce. Todo lo demas se cuelga de ella:

  • Por cada PV el sistema espera un tag que la mida, y ademas dos tags de limite (_lmin y _lmax) que le dan la escala a la fuzzificacion.
  • Por cada SP espera un tag donde escribir y una tabla defuzzy que traduzca las acciones en incrementos.
  • Las reglas solo pueden nombrar variables que esten aqui.

Por que existe como lista aparte: desacopla el razonamiento de la instrumentacion. El experto habla de "nivel de hopper", no de PCS7.OS01.Hopper_Nivel_PV_A, asi que si manana cambia el nombre del tag en KEPserver solo se reasigna el enlace y las reglas siguen intactas.

Como llenarlo sin trabajo manual: pulsa Sincronizar con tags. Toma los identificadores de tus tags PV y SP, arma el contrato y asigna los roles de esos tags automaticamente. Despues quitas a mano las variables que este cliente no use — que es justo lo que este proyecto necesita, al ser un estandar que se moldea.

Lo unico que queda manual son los limites: que PV acota cada tag LIM no se puede deducir del nombre, y equivocarse ahi descalibra la fuzzificacion en silencio. Ese enlace se hace en la tabla de Tags KEPserver, columna Rol.

Quitar una variable no es borrar una fila: arrastra su modelo difuso, su filtro, sus limites, las reglas que la nombran, los permisivos y el mapeo de tags. Usa "Ver impacto" antes de guardar. Al guardar, el nucleo toma la lista nueva sin reiniciar. Lo unico que no cambia en caliente es el motor: si esta corriendo, detenelo y volve a arrancarlo — cambiar el contrato bajo un lazo en marcha significaria fuzzificar contra otra escala a mitad de tick.

Variables

Catalogo de variables crudas (sensores) y definiciones calculadas. Las definiciones se procesan en orden; una calculada puede referenciar crudas, PVs o una definicion previa. El motor las calcula en cada tick: una vez definida, una calculada se comporta como una PV mas — se le puede crear un fuzzy y nombrarla en reglas y permisivos. Para fuzzificarla necesita lmin/lmax: asignale tags <nombre>_lmin / <nombre>_lmax en Tags KEPserver, o deja los limites de respaldo de esta tabla.

Variables de entrada (PV)

Se toman de los tags de categoria PV, no se escriben a mano. El identificador se genera del pseudonimo del tag y queda fijo: es lo que ven las reglas. La descripcion es libre y editarla no rompe nada. Para cambiar el identificador usa Renombrar, que te muestra el impacto antes de aplicar.

Definiciones calculadas (orden importa)

Tracking PV-SP

Bloqueo por seguimiento entre el valor de proceso (PV) y el setpoint objetivo (SP). Mientras |PV - SP| > rango, la familia queda bloqueada y el motor no emite nuevas acciones sobre ella.

Como funciona el Tracking

Cada familia de setpoint — una por cada tag de categoria SP — puede tener asociado un PV de readback que mide el valor real del proceso. Cuando el motor de reglas emite una accion que modifica un SP, el tracking compara el PV actual contra el SP objetivo.

Si la diferencia |PV - SP| supera el rango configurado, la familia queda bloqueada: no se emiten nuevas acciones sobre ese SP hasta que el PV entre en la banda [SP - rango, SP + rango].

Esto evita oscilaciones: el sistema espera a que el proceso alcance el objetivo antes de actuar de nuevo. Si una familia esta deshabilitada o no tiene readback, el tracking no la bloquea (comportamiento clasico sin tracking).

Arranque bumpless. Cada vez que el DCS entrega el lazo (el handshake ENABLE_FBK pasa de denegado a concedido), el SP de la familia se lleva al valor con el que el equipo venia operando, antes de volver a escribir, para retomar sin salto. De donde sale ese valor lo decide la columna Arranque: el SP de referencia del DCS (lo habitual: el setpoint que el operador ve en el HMI), el PV de readback, o ninguno (retomar con el ultimo valor del SE). Es independiente del interruptor Habilitado, que solo controla el bloqueo por seguimiento. Si la referencia no se puede leer, la familia no se escribe hasta poder leerla: retomar con un valor inventado es el salto que esto evita.

⚙ Generador de Datos para KEPserver DETENIDO

Genera valores dinamicos (3 fases: estable, alerta, recuperacion) y los escribe al KEPserver periodicamente. Escribe unicamente los tags listados abajo (generator.ranges en tags.json). Los booleanos del handshake — ENABLE, HEARTBEAT, LIC_AUTO/MANUAL y selectores — quedan fuera a proposito: son señales de protocolo y llenarlas de ruido rompe el enclavamiento del lazo experto.
Es independiente del Sistema Experto: puedes moverlo con el boton Iniciar de aqui abajo aunque el SE todavia no arranque por mapeo incompleto.
Marca solo los tags que quieras simular. Los desmarcados no se escriben nunca — usalo para que el generador rellene las señales que faltan sin pisar las que ya vienen de planta. Los tags nuevos que des de alta aparecen aqui solos, desactivados, para que nada se escriba por accidente.

🔐 Handshake con el DCS (ENABLE) SIN CONFIGURAR

Es el permiso del DCS para que el experto escriba. El SE lo pide escribiendo el tag EXT, y el DCS responde en el tag FBK. Es fail-closed: mientras el FBK no diga que si —o no se pueda leer— no sale ningun setpoint. Un handshake que no se puede leer es indistinguible de uno denegado.

Deshabilitado, el SE escribe sin pedir permiso. Solo tiene sentido en una planta donde el bloqueo lo hace el propio DCS.

Solo aparecen tags OTRO y habilitados. Tras habilitar o crear uno, pulsa Actualizar valores arriba.

¿Como funciona el Heartbeat?

Concepto: Un heartbeat es un pulso periodico que confirma que dos sistemas (esta app y el PLC / KEPserver) siguen comunicandose. No transporta datos de proceso; solo demuestra que el canal esta vivo.

Flujo por tick:

  1. La app alterna entre Valor A y Valor B (tick par → A, impar → B).
  2. Escribe ese valor en el tag OUT via OPC-UA.
  3. Lee el tag IN, que el PLC debe copiar desde OUT (loopback en la logica del PLC).
  4. Si IN == OUT y ambos tags responden, se marca Eco OK → la comunicacion bidireccional esta viva.
  5. Espera Frecuencia Tick segundos y repite.

Parametros editables:

  • Tag OUT / Tag IN: nombres de los tags KEPserver usados como pulso.
  • Frecuencia Tick (s): intervalo entre pulsos (min 0.2 s).
  • Valor A / Valor B: los dos valores que se alternan.
  • Tipo de dato: Float, Int o Boolean (segun como este configurado el tag en KEPserver).

Independiente del motor SE: el heartbeat corre en su propio hilo. Puede iniciarse / detenerse sin afectar el Generador de datos ni el Sistema Experto. La configuracion se persiste en tags.json.

Informacion sobre Tags KEPserver

Formato de tag: Canal.Dispositivo.Variable (ej: PCS7.OS01.PU009_Velocidad_PV)

Tipos soportados: Float, Int, Boolean, String.

Categoria: se elige manualmente al agregar el tag y puede cambiarse despues desde el selector de la columna Categoria. Ya no se deduce del prefijo del nombre, asi que funciona con cualquier nomenclatura de planta (PCS7, OS01, etc.). La categoria organiza y documenta el tag; el motor del SE sigue resolviendo que leer y escribir por el nombre exacto del tag.

Conectividad: El sistema intenta conectarse via OPC-UA a opc.tcp://127.0.0.1:49320. Si el KEPserver no esta disponible, los tags se mostraran como desconectados pero su configuracion se mantiene.

Tags suspendidos: No se leeran ni escribiran al KEPserver mientras esten suspendidos. Esto es util para desactivar temporalmente un tag sin eliminarlo.
