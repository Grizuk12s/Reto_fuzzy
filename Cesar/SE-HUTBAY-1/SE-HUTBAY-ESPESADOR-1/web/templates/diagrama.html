Entrada de Datos
Variables de proceso, sensores crudos y limites fuzzy
Simulacion / Tags KEPserver

El sistema soporta dos modos de entrada:

Simulacion ON Se generan datos sinteticos con simulacion.py en 3 fases (estable, alerta, recuperacion) y el generador de datos (TagGenerator) escribe valores dinamicos en KEPserver.

Simulacion OFF Se leen directamente los tags reales del KEPserver via OPC-UA. Los tags deben tener valores reales proporcionados por el proceso o un sistema externo.

Variables PV (9) RETO.PV.torque, RETO.PV.bed_mass, RETO.PV.bed_level, RETO.PV.densidad, RETO.PV.torque_bomba, RETO.PV.potencia_bomba, RETO.PV.presion_descarga, RETO.PV.presion_diferencial, RETO.PV.nivel_rastra Sensores crudos (6) RETO.CRUDA.tonelaje_sag_1/2, RETO.CRUDA.tonelaje_relave, RETO.CRUDA.presion_bomba_1/2, RETO.CRUDA.turbiedad_agua Limites fuzzy (18) RETO.LIM.{var}_lmin, RETO.LIM.{var}_lmax por cada PV Protocolo OPC-UA (opc.tcp://127.0.0.1:49320) — lectura batch en una sola conexion

4
Filtro Exp-Q
Suavizado exponencial cuadratico para reducir ruido

Cada variable de proceso pasa por un filtro de media ponderada exponencial: y = ∑ wi · xk-i / ∑ wi donde wi = exp(-q · i²).

Parametros q (peso decaimiento) y window_size (muestras) por variable Ejemplo torque: q=0.15, ws=10 | bed_level: q=0.20, ws=8 Efecto Reduce ruido manteniendo tendencia; q alto = mas filtrado Estado Mantiene buffer deque entre ticks (memoria temporal)

Clase: ExpQFilter.actualizar(inputs_raw) -> inputs

inputs (9 floats filtrados)
5
Fuzzificacion
Conversion de valores numericos a etiquetas linguisticas con grado de pertenencia

Cada variable se evalua contra sus funciones de membresia (modelos tipo high, low, norm) para obtener grados de pertenencia μ a etiquetas linguisticas.

Etiquetas base LOW OK HIGH Pendientes DEC STABLE INC (regresion lineal en ventana de 60s) Compuestas NO-HIGH NO-LOW CERCA_ALTO CERCA_BAJO Formula NO-* μ(NO-X) = 1 - μ(X) Formula CERCA CERCA_ALTO = min(μ(OK), μ(HIGH))

Salida: fuzzy_out = {torque: {dom: "HIGH", val: 0.85, pert: {HIGH: 0.85, OK: 0.15, LOW: 0.0, ...}}, pend_torque: {...}, ...}

fuzzy_out (etiquetas + μ)
6
Evaluacion de Permisivos
Condiciones logicas que habilitan/bloquean acciones del motor

Los permisivos son condiciones booleanas complejas (AND/OR/NOT) que verifican el estado del proceso. Se inyectan en fuzzy_out como pseudo-variables __PERM_* con etiquetas ON/OFF (μ=1 o 0).

PERMITIR_FRENAR_DESCARGA ON cuando NO hay alertas criticas en SAG/tonelaje/tendencias PERMITIR_SOLTAR_DESCARGA ON cuando NO hay alertas en presiones/torque de bombas OPTIMIZAR_SUBIR_DENSIDAD ON cuando condiciones favorecen subir objetivo de densidad OPTIMIZAR_BAJAR_DENSIDAD ON cuando condiciones favorecen bajar objetivo

Mecanismo: Las reglas refieren a __PERM_* en su if. Si el permisivo esta OFF, la regla que requiere ON no dispara.

fuzzy_out + __PERM_* inyectados
7
Motor de Reglas
Evaluacion jerarquica de reglas con bloques, prioridades y cooldowns

El motor evalua todas las reglas contra fuzzy_out usando logica AND/OR/NOT. Las reglas se agrupan en bloques jerarquicos.

Belief belief = weight × min(μ(condiciones)) — umbral minimo 0.05 Bloque critico Nivel 1 — si dispara, bloquea estabilidad Bloque estabilidad Nivel 2 — bloqueado si critico disparo Bloque optimizacion Independiente — siempre se evalua Cooldown vel_bomba: 900s | floculante: 1800s | tonelaje: 2700s — por familia de SP

Salida: Lista de eventos con {regla_id, bloque, acciones, belief}

eventos fired [{accion, belief}, ...]
8
Defuzzificacion (Sugeno)
Conversion de acciones fuzzy a cambios numericos en setpoints

Cada accion disparada se traduce a un delta numerico sobre el setpoint correspondiente, interpolando en tablas de Sugeno segun el belief.

Acciones AUMENTAR|DISMINUIR + VEL_BOMBA|TONELAJE|FLOCULANTE + FUERTE|SUAVE|(normal) Interpolacion step = np.interp(belief, belief_axis, steps) Aplicacion SP[familia] += step, luego clamp a limites [LL, HL] Acumulativo Multiples reglas en un tick aplican secuencialmente sobre el mismo SP

Ejemplo: DISMINUIR_VEL_BOMBA_FUERTE @ belief=0.8 → step=-0.4 → sp_vel_bomba -= 0.4

setpoints actualizados
9
Salida: Setpoints Actualizados
Nuevos valores de consigna para el proceso Prueba/Demo

Los 3 setpoints se actualizan en cada tick y se acumulan entre iteraciones. En modo KEPserver, los valores se escriben de vuelta a los tags RETO.SP.* via OPC-UA.

sp_vel_bomba Velocidad de la bomba de descarga → RETO.SP.sp_vel_bomba sp_tonelaje Tonelaje objetivo de alimentacion → RETO.SP.sp_tonelaje sp_floculante Dosificacion de floculante → RETO.SP.sp_floculante Persistencia Los SPs se arrastran al siguiente tick como estado mutable Escritura KEPserver OPC-UA write a RETO.SP.*  |  Simulacion solo en memoria
↻ Se repite cada 5 segundos (configurable). Lee tags → ejecuta pipeline → escribe SPs. El estado (filtros, hist, cooldowns, SPs) se arrastra entre iteraciones.
